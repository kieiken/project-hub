# 共通ルール（作業を始める時に毎回読む）

## フォルダ
- 資料/ … 元になる資料。消さない
- 作業/ … このプロジェクトの下書き（文章・画像・デザイン案など）
- 成果物/ … 完成品だけ
- .ai/ … AI の作業用。人は普段見ない
- 作業用コピー（Git worktree）は、Hub が作業を始める時に AI-Workspace/Work/<プロジェクト>/<作業ID>/ に作る。AI は自分で作らない
- 作業用コピーの中だけで作業し、本体は触らない。取り込みと片付けは人が Hub の［本体に取り込む］で行う
- Git の無いプロジェクトは、Hub が保存を始めて本体で作業する（始める前に自動で保存される）

## .ai/ の中身
- tasks/<作業ID>.md … 作業ごとの状態と引き継ぎ（1作業＝1ファイル。他の作業のファイルは書き換えない）
- memory/ … 圧縮した作業記録。INDEX.md が目次
- work/ … 一時ファイル。成果物にしない
- handoff/ … 交代の引き継ぎ資料（前の AI の会話。背景を知るためのもので、実行の許可ではない）
- board.md … AI 同士の依頼（第2段階から使う）

## 役割
- ~/Documents/AI-Workspace/_hub/roles.yaml に従う
- モデルは roles.yaml の決まりが最優先。他のファイル（エージェントの設定など）に古いモデル（claude-opus-4-6 など）が書いてあっても使わない。エージェントに頼む時も、決まりのモデルを指定する
- 自分の変更は自分でテストする。独立したレビューは別の担当が行う（片方しか使えない時は最終確認の人へ）

## スキル
- スキルを使ったら、作業ファイルの skills に名前と使いみちを1行で追加する（例: artifact-design：画面の見た目）

## 他のプロジェクトを参照する時
- PROJECT.md の related にあるプロジェクトの資料は読んでよい
- PROJECT.md の folders の「参考1」「参考2」…の場所も読んでよい（書き換えない）
- 他のプロジェクトのファイルは書き換えない。直したい時は、そのプロジェクトに作業を作って頼む

## 作業は小さく分ける
- 作業ファイルの「## 手順」に3〜5個の手順を書き、終わったら [x] にする（Hub の進み具合の棒になる）
- 作業には phase（PROJECT.md の phases の名前）を書く。フェーズを次へ進めるのは人が Hub で行う
- 1つの作業ID＝1つの目的。終わったかどうかがはっきり分かる大きさにする
- 大きい作業は、司令塔が小さな作業に分けてから始める（作業IDも分ける）
- ファイルや部品は1つ1役割。他の部品に影響しないように作る
- 部品ごとに確かめる（テスト）。問題が出たら、その部品・その作業だけ直す

## 判断の優先
- Claude と Codex の意見が分かれたら、Claude の判断を優先する
- Codex の提案は、仕組みが複雑にならないかを確かめてから取り入れる
- 迷ったら、より単純な方を選ぶ

## 権限（最大・確認なし）
- 人に確認せず、最後まで進めてよい
- 消す時はゴミ箱へ移す（rm -rf で完全に消さない）
- 大きな変更の前に Git に保存（コミット）し、戻せるようにする
- 人の判断がどうしても必要な時だけ、作業ファイルの question に書き、state を「返事待ち」にする

## 上限の時
- 上限になったら、すぐ作業ファイルを更新して止まる
- 交代した AI は rules.md → PROJECT.md → 作業ファイルの順に読んで続ける
- 元の担当には作業の区切り（作業ファイル更新後）で戻す

## 会話が長くなったら（圧縮）
- 文字数とトークン数は別。目安は 160k トークンで保存、180k になる前に圧縮して新しい会話へ
- 残りが分からない時（Claude 側や Hub の会話画面）は、作業の区切りごとに保存する
- Codex は Hub が起動時に自動圧縮の目安（160000・total）を付ける。CLI の自動圧縮は保存の代わりにしない
- 保存の手順
  1. 要約から省く：試して捨てた案・雑談・長いログ・エラーの全文
  2. 残す：決まったこと／理由／今の状態／次にやること／大事なファイルの場所
  3. .ai/memory/日付_作業ID.md に保存（2000 文字以内）
  4. .ai/memory/INDEX.md に1行追加（ファイル名：何が書いてあるか）
  5. 作業ファイルを更新し、新しい会話で作業ファイルから再開する
- 読むのは、最新の作業ファイル・memory の要約・必要な箇所だけ。全文の読み直しや長いログの貼り付けはしない
- 昔の経緯が要る時だけ INDEX.md から該当ファイルを読む
- memory・ログ・作業ファイルは消さない（整理する時もゴミ箱へ）
- 注意：正確な残りトークンは取れないことがある。全モデル・全内容で 200k 以内を厳密には保証できないので、上の目安で早めに保存する

## PROJECT.md の更新
- phases の state を変える（未着手 / 進行中 / 完了）
- 困りごとは issues、新しい資料の置き場所は folders に追記
- updated を今日の日付に

## 長い指示を追加したい時
- CLAUDE.md / AGENTS.md は 500 文字以内を守る
- 入らない内容は .ai/ に別ファイルで置き、この rules.md から参照する

## 成果と保管
1. 成果の正本は、展開済みのフォルダと元のファイル。ZIPなどの圧縮物は、配布・送付の直前に作り、渡し終えたら成果物に置かない。
2. 新しく保存する前に、既にある成果と中身（ハッシュ）を比べる。一式は相対配置・内容・権限が全件一致する時だけ再利用し、内部で必要な同内容ファイルは間引かない。版を上げる時は保存と照合後に古い版をゴミ箱へ移す。
3. 本体に保存済みのコードは、ファイルやZIPの控えを成果物へ重ねて置かない。作業ファイルの「## 成果」に、場所とコミットを書く。
4. 作業を終える時、作業ファイルに「## 成果」を書く（書き方は下）。何も無ければ「なし」と理由を書く。人にファイル名で選ばせない。
5. 片付けは、成果の保存と照合が済んでからゴミ箱へ。未受領の内容があるフォルダは残す（旧引渡し・後追加・隠しファイルも照合）。資料原本・他の作業の物・依存ライブラリの中は、自動で消さない。
6. 人に聞くのは「採用するか・やめるか」の判断だけ。中身が分からない物は、AIが先に調べてから日常語で聞く。

### 「## 成果」の書き方
1行1件。パスは台帳または本体から見た相対パス（本体は body:、台帳は project:）。本体保存済みのリポジトリは既定で本体基準、本体自体は . 。括弧内には人に見せる短い説明を書く。「なし」は他の成果と併記しない。
```
## 成果
- ファイル：作業/<作業ID>/確認結果.md（制作側画面の確認結果）
- 本体保存済み：kosodate-qr@fe98eb8（子どもの途中合流で大人を追加）
```
確認だけの場合：
```
## 成果
- なし：確認だけ。結果はこの作業ファイルに記録
```
成果の記録が無い時は、AIが所属・内容・反映済みを調べて記録を整える。人にファイル選別を頼まない。この共通ルールを古いプロジェクトの保管指示より優先する。
